# Render → Critique → Repair — execution evidence protocol

A substantial REDESIGN/REBUILD should create a working experience, not only a longer prompt or design plan. A small PATCH needs proportionate checks, not the full ceremony. No tool access means explicit UNKNOWN.

1. **Truth:** inspect existing product/code/rights/routes, assets and protected contracts. Label observed, supplied-unverified, hypothesis, unknown.
2. **Direction:** select one ownable spatial/material/behavioral idea grounded in actual job; compare alternatives when direction unsettled.
3. **Build:** deliver functional opening, meaningful middle and completion/decision, adapted to user job. The sequence is not a mandatory three-section marketing template.
4. **Render:** inspect real desktop + mobile screens and relevant interactive state. Record URL, browser, viewport, build SHA and assets. On motion-heavy sites inspect normal AND reduced motion, not only animations-disabled screenshots.
5. **Critique:** identify the single most consequential weak link: hierarchy, middle repetition, unverified proof, broken action, visual brand mismatch, inaccessible task or performance. Distinguish subjective taste and observed defects.
6. **Repair actual cause:** change architecture, copy, media, interaction or code rather than decorating a broken scene; preserve strengths and legally/business-critical data.
7. **Retest:** take equivalent captures and tests, document changes and compare with dated evidence. If browser is unavailable mark NOT VERIFIED; don't fabricate improvement, approval or human testers.

**Two lanes:** task/browser/keyboard/CTA/error/contract correctness and art/motion/composition/real mobile. Neither substitutes for the other. No score can compensate for a severe falsity or broken user journey. Stop when requested work is complete and no known fixable critical blocker remains within authorized scope; report concrete unknowns.
